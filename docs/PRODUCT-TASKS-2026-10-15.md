## 4. P0 实施任务

### P0-01 测试资金与钱包安全

本次：移除前端私钥、自动补助签名与发币路径；保留用户钱包自行调用既有 faucet。领取前核对账户、链 ID、原生 Gas 余额和估算费用；零余额不给出虚假到账提示；显示明确链名及币种。成功只在 receipt 成功后显示完整交易 Hash。Fuji 可链接官方测试水龙头；L1 未启用自动补助时明确说明，不承诺无限领取。

后续受控服务方案：独立测试 Gas 钱包，只允许 chain 11230 白名单；服务端密钥放托管 secret store，前端仅调用请求 API。钱包挑战签名证明地址所有权，短期 nonce、防重放；按地址、IP、时间窗设置限流，单次额度、每日总额、余额阈值和并发幂等键。默认关闭，人工授权开启；密钥从不来自 iris 私人钱包。余额不足熔断，提供监控与报警。额度按实测交易费用确定，不固定承诺“1 LUSD”或“无限次”。部署、注资、密钥权限及速率策略批准后才启用。

已公开的旧密钥即使从最新代码移除，也仍可能存在 Git 历史和缓存。不要再向对应钱包注资；如需新补助，生成独立钱包，是否迁移旧测试资产另行授权。此次不重写历史清密钥，不自行转移其余额。

### P0-02 阶段内交付与防误导

订单包含阶段，阶段包含交付版本。当前阶段展示交付入口、金额、名称与真实状态；未开始阶段不可提交。右侧保留资金与参与者，争议置于次要“遇到问题”入口。当前合约未单独保存阶段要求，使用已有名称与项目说明，不虚构已存在的字段。

本次允许引用对方可访问的 http(s) 链接、填写公开交付说明并选择实际文件计算 SHA-256。必须明确“选择文件不上传”，不能仅凭本地指纹提交无链接交付。异步计算期间阻止提交，重新选文件清理旧指纹，失败可重试。正式提交失败保留输入。链接访问/下载需双方另行确认，静态站不能可靠验证第三方鉴权、内容变化或下载可用性。

SHA-256、文件名、链接、说明通过现有 delivery 参数关联阶段，并以成功交易与 `Delivered` 事件建立时间、身份和凭证证据。历史事件用于展示 V1/V2，不以本地缓存伪装不可变历史。指纹相同仅表示字节一致，不证明质量或版权。

## 6. 页面与状态流程

- 订单：项目说明与进度；阶段列表中的当前交付/验收；阶段历史；资金和参与者；后续私密沟通。
- 文件：未选择 → 计算指纹 → 本地计算完成（不等于上传）→ 交付链接与说明确认。
- 后续上传：上传中 → 已保存可预览 → 待正式提交；上传失败可重试，不进入待验收。
- 交易：待钱包确认 → 已广播/等待链上确认 → receipt 成功/待验收；拒签、余额不足、RPC 失败、revert 均不显示交付成功。
- 验收：已提交 → 按既有合约验收并放款 → 已付款；receipt 与事件是依据。此合约验收与释放在同一调用中，不虚构独立的支付队列。
- 超时：现有 `claimAfterTimeout` 在验收期满足后由接单人主动调用，不是后台自动付款。保持原规则。
- 争议：调用既有 dispute/resolve；不推断未来仲裁制度已上线。
- 网络：明确 Fuji / L1。失败不静默切链并显示同编号其他链订单；用户主动切换时清晰保留币种边界。
