# Landed V2

V2 是新合约 `contracts/LandedV2.sol`。V1 的 `Landed.sol` 没改，V1 的功能和规则在 V2 里都还在。

## 改了什么

1. **雇用后可以改需求**
   客户或已雇用的自由职业者都能发起 `proposeChange`，改的是还没付款的里程碑（名称、金额、审核期）。对方 `acceptChange` 后生效，任一方都能 `cancelChange` 撤回。
   - 新总额更高：接受时从客户那里补差价。如果是自由职业者发起的，客户接受前要先给合约授权代币。
   - 新总额更低：差价直接退给客户。
   - 每个工作同时只能有一个待处理提案。当前里程碑已提交审核时不能提案。付款或进入争议后，未处理的提案自动作废。
2. **可更换仲裁人**
   部署者是 owner，可以用 `setArbiter` 换仲裁人。争议由**处理时**的仲裁人裁决。
   owner 转移分两步：`transferOwnership` 指定新地址，对方 `acceptOwnership` 确认，防止转错地址。
3. **双方协商取消**
   进行中的工作，一方 `requestMutualCancel`，另一方 `confirmMutualCancel`，托管里剩下的钱全部退给客户，状态变成 Cancelled。发起方可以用 `withdrawMutualCancel` 撤回。

## 为什么

V1 雇用后条款就锁死了：需求变了、要换仲裁人、双方都想散伙，都只能走争议。V2 让双方在不打官司的情况下自己商量着改。

## 以后怎么部署

（这次没有部署。）

1. `npm run compile`，确认 `build/LandedV2.json` 生成。
2. 现在的 `scripts/deploy.js` 部署的是 V1（`artifact("Landed")`）。部署 V2 时把它改成 `artifact("LandedV2")`，并把输出文件换个名字，免得覆盖 `deployments/fuji.json` 里的 V1 地址。
3. 私钥只放在本地环境变量或本地 `.env` 的 `DEPLOYER_PRIVATE_KEY` 里，不要提交到仓库。运行：
   ```
   NETWORK=fuji npm run deploy
   ```
4. 把前端指向新地址。

## 注意：新地址，老工作留在 V1

合约部署后不能升级，部署 V2 会得到一个**新地址**。V1 上已有的工作、托管资金和信誉记录都留在 V1 合约里，照常用 V1 完成或取消。V2 从零开始，只管新发布的工作。
